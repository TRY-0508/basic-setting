# 一致性与变更管理

解决大型项目中"每次修改前都要反复检查一致性、写临时方案文档再合并"的低效问题。

> 本 skill 生成的提案、报告和检查结果均遵循 `project-workflow` 中的文档编写规范：平实语言、具体而非抽象、不堆砌术语、不用虚饰限定词。

## 核心理念

**行内提案替代临时文档。** 传统流程的问题：

```
旧流程：检查一致性 → 写临时方案文档 → 按方案执行 → 合并回正式文档
        └─ 检查无标准 ─┘  └─ 版本分裂 ─┘          └─ 合并易错失上下文 ─┘
```

新的行内提案流程：

```
新流程：影响分析 → 在设计文档中写入行内提案 → 用户审核通过 → 直接执行
        └─ 有标准检查 ─┘  └─ 上下文不丢失 ─┘  └─ 无合并步骤 ─┘
```

## 1. 变更提案流程

### 1.1 标准流程

当用户提出一个涉及跨模块或可能影响已有设计的变更请求时：

```
用户请求
  │
  ├── Step 1: 加载相关文档
  │   从 INDEX.md 找到受影响模块的设计文档
  │   加载系统 design.md 中的模块契约
  │
  ├── Step 2: 影响分析
  │   输出：受影响模块列表、涉及契约、风险等级
  │   向用户确认影响范围是否准确
  │
  ├── Step 3: 写入行内提案
  │   在受影响的 design.md 中以 [!PROPOSAL] 标记写入变更提案
  │   提案紧跟被影响的段落，上下文清晰
  │
  ├── Step 4: 用户审核
  │   用户可以直接看到提案在文档中的上下文
  │   可接受、修改或拒绝
  │
  ├── Step 5: 执行
  │   移除 [!PROPOSAL] 标记
  │   将提案内容变为正式内容
  │   更新受影响的契约、接口声明
  │
  └── Step 6: 验证
      检查 INDEX.md 中模块状态是否需要更新
      检查是否有契约违反
```

### 1.2 行内提案格式

在被影响的文档段落下直接插入：

```markdown
> [!PROPOSAL]
> **提案**：[一句话描述变更]
> **影响范围**：module-a、module-b
> **契约变更**：
> - core-api：`getUser()` 返回类型增加 `role` 字段
> - 新增契约：auth → notification
> **改动概要**：
> 1. core 模块 user 模型增加 role 属性
> 2. auth 模块登录后推送 role 变更事件
> 3. notification 模块新增 role-change 监听
> **风险**：低。仅新增字段，不改变现有接口签名。
> **待确认**：role 字段是否需要对旧数据做回填？
```

**提案规则：**
- 提案紧跟被影响的文档段落，不要单独放在文件末尾
- 每个提案必须有"待确认"项，明确需要用户决策的点
- 如果提案影响多个模块文档，在每份文档中都插入对应的提案块（包含完整的"影响范围"信息以保持上下文）
- 提案是**临时的**——一旦用户批准并执行，立即删除 `[!PROPOSAL]` 块

### 1.3 对比：为什么不用临时文档

| 方面 | 临时文档方案 | 行内提案方案 |
|------|------------|------------|
| 上下文 | 需要来回切换文档查看上下文 | 提案紧跟被影响的段落 |
| 合并 | 需要手动将临时文档内容合并回正式文档 | 无合并步骤，直接就地修改 |
| 遗漏风险 | 合并时容易遗漏或错位 | 上下文绑定，不容易遗漏 |
| 版本混乱 | 临时文档和正式文档可能不同步 | 只有一份文档，只有"正式+提案块" |
| 回顾 | 事后很难找到当时的方案 | 如果需要回顾，可从 git history 看到被移除的提案块 |

## 2. 影响分析

### 2.1 分析清单

每次变更前，按以下清单逐项检查：

```markdown
## 影响分析

### 直接影响的模块
- [ ] module-a：原因（具体接口/契约变更）
- [ ] module-b：原因

### 间接影响的模块（依赖受影响模块的）
- [ ] module-c：通过 contract-x 间接影响

### 契约变更
- [ ] 已有契约修改：[列出契约名和具体变更]
- [ ] 新增契约：[新增的模块交互]

### 文档需要更新
- [ ] INDEX.md：模块状态变更
- [ ] 其他模块 design.md：接口变化通知

### 代码层面
- [ ] 接口签名变更
- [ ] 数据模型变更
- [ ] 配置变更
- [ ] 测试用例需要更新
```

### 2.2 影响分析方法

1. **从 INDEX.md 出发**：查看模块依赖关系表
2. **追溯契约**：找出契约中引用被修改接口的所有模块
3. **代码搜索**：grep 被修改的函数名/类型名/接口名
4. **输出分析结果**：以表格形式列出所有受影响项，标注风险等级（高/中/低）

## 3. 一致性检查

### 3.1 检查维度

| 维度 | 检查内容 | 方法 |
|------|---------|------|
| 文档-代码一致性 | design.md 中的接口定义是否与代码匹配 | 对比接口签名 |
| 契约一致性 | 模块 A 的"对外接口"是否与模块 B 的"依赖声明"匹配 | 交叉读取两端的声明 |
| 文档间一致性 | 系统 design.md 的模块清单是否与 modules/INDEX.md 一致 | 对比模块列表 |
| 接口完整性 | 每个模块是否声明了所有对外接口和依赖 | 对照代码中的公开 API |
| 状态一致性 | INDEX.md 中的模块状态是否与实际进度匹配 | 对比 workplan 完成情况 |

### 3.2 检查触发时机

- 用户说"检查一下现在的文档有没有问题"
- 用户说"代码改了，帮我更新文档"（代码→文档反查）
- 新增了一个模块但没写文档
- 用户提到"感觉文档有点乱"

### 3.3 检查输出格式

```markdown
## 一致性检查报告

### 通过 ✓
- module-a: design.md 接口定义与代码一致
- core-api 契约：consumer 声明与 provider 声明匹配

### 问题 ✗
| 问题 | 严重程度 | 涉及文档 | 修复建议 |
|------|---------|---------|---------|
| modules/INDEX.md 缺少 module-c | 中 | modules/INDEX.md | 添加 module-c 条目 |
| auth design.md 声明的依赖 core-api:v2 与系统 design.md 中的契约版本 v1 不一致 | 高 | auth/design.md, design.md | 统一版本号 |
```

## 4. 代码→文档反查

当用户修改了代码后要求更新文档时：

1. **定位变更**：从 git diff 或用户描述确定改了什么
2. **确定影响范围**：按 2.1 清单分析
3. **直接修改文档**：在对应 design.md 中更新接口定义、数据模型等
4. **不要写提案**：代码已经改了，直接更新文档反映事实状态
5. **检查契约**：如果接口变化导致契约破坏，输出问题报告让用户决策

## 5. 常见反模式

| 反模式 | 问题 | 正确做法 |
|--------|------|---------|
| 先改代码再补文档 | 文档滞后，后续变更缺少上下文 | 先走提案流程，批准后再改代码 |
| 提案放在文档末尾 | 脱离上下文，难以理解影响 | 提案紧跟被影响的段落 |
| 提案过于简略 | 用户无法判断影响范围 | 必须包含影响范围、契约变更、风险 |
| 跳过影响分析直接写提案 | 可能遗漏间接影响的模块 | 先用 INDEX.md 追溯依赖链 |
| 批准后忘记删除提案标记 | 文档残留临时内容 | 执行变更时同步删除 `[!PROPOSAL]` |
